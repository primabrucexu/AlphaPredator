## What

### 已确认需求

- 提供一个通用的任务处理模块，为后续回测等耗时操作提供统一的运行和查询能力。
- 用户可以看到总任务的处理状态和进度。
- 一个总任务可以拆分成多个子任务，用户可以看到每个子任务的状态和进度。
- 所有总任务继续串行执行；`COMPUTE` 总任务内的子任务允许受控并行，`EXCLUSIVE_UPDATE` 总任务及其子任务保持串行。
- 任务调度策略分为允许普通排队的 `COMPUTE` 和优先排队的 `EXCLUSIVE_UPDATE`；数据更新任务不抢占正在运行的任务。
- 前端提供独立任务页面；所有业务任务的创建入口统一放在任务页面。
- 后端任务框架代码统一放在 `backend/app/tasks/`，业务通过 Handler 接入。
- Worker 使用独立进程，首次出现待处理任务时按需启动；队列清空后继续等待 60 秒，连续空闲后自动退出。
- Handler 通过 `build_items()` 声明需要循环处理的元素，任务框架在创建总任务时自动生成并持久化子任务。
- 每个任务至少包含一个子任务；没有天然循环的任务由 `build_items()` 返回单个元素，不提供绕过子任务的执行路径。
- F002 只负责通用任务能力，不预先定义具体的回测业务规则。

### 第一版范围

- 提供任务列表和任务详情页面。
- 展示任务名称、任务类型、状态、总体进度、子任务完成数量、创建时间、开始时间、结束时间和最近状态说明。
- 在任务详情中展示全部子任务及各自的状态、进度、耗时和失败原因。
- `TaskService` 支持创建任务，公开 API 支持查询任务和请求取消任务；任务取消采用协作式取消，在安全检查点停止。
- 使用一个按需启动的独立本地 Worker 串行领取总任务，并在同一进程内按调度策略执行子任务。
- 任务及子任务状态持久化，刷新页面或重启 Web 服务后仍可查看历史记录。
- 任务执行失败时保存可供用户理解的错误摘要，不把任务伪装成成功，也不生成伪造结果。
- F002 没有生产业务 Handler；自动化测试使用测试专用 Handler 验证任务生命周期。

### 第一版非目标

- 不实现具体的回测参数、回测算法、行情准备和结果分析。
- 不实现多 Worker、多个总任务并行、跨机器调度和定时任务。
- 不提供页面级并行度配置；计算子任务并行度仅通过后端环境变量配置。
- 不实现用户可配置的优先级；第一版只提供固定的“数据更新优先于计算任务”规则。
- 不实现暂停后继续、自动重试、失败子任务单独重跑和任务依赖编排。
- 不实现任务历史删除或自动清理。
- 不提供完整日志检索系统；第一版只保存状态说明和错误摘要。
- 不使用 WebSocket 或 SSE；第一版由前端定时轮询任务状态。
- 不迁移韭研涨停同步、股票目录刷新或其他现有业务操作；这些内容归入 F002.1。

## How

以下内容为已确认并实现的第一版设计。

### 1. 核心概念

#### Task（总任务）

一次由用户发起的完整工作。例如未来的“一次回测”可以对应一个 Task。

建议字段：

| 字段 | 说明 |
|------|------|
| `id` | 任务唯一标识 |
| `task_type` | 任务类型，由业务模块注册，例如未来的 `backtest` |
| `scheduling_policy` | 固定调度策略：普通排队的 `COMPUTE` 或优先排队的 `EXCLUSIVE_UPDATE` |
| `title` | 面向用户展示的任务名称 |
| `status` | 当前状态 |
| `total_items` | 子任务总数 |
| `completed_items` | 已成功完成的子任务数 |
| `failed_items` | 失败的子任务数 |
| `progress` | 总体进度，取值 0 到 100；无法计算时为空 |
| `status_message` | 最近一条面向用户的状态说明 |
| `input` | 创建任务所需的非敏感参数快照 |
| `result` | 任务结果摘要或结果引用，不承载大体积结果 |
| `error` | 总任务失败原因摘要 |
| `created_at` / `started_at` / `finished_at` / `updated_at` | 生命周期时间 |
| `cancel_requested_at` | 用户请求取消的时间 |

#### TaskItem（子任务）

总任务内部可独立报告进度的处理单元。例如未来可以按股票、参数组合或数据分片拆分，但具体拆分规则由回测 Feature 决定。

建议字段：

| 字段 | 说明 |
|------|------|
| `id` / `task_id` | 子任务标识及所属总任务 |
| `sequence` | 稳定展示顺序 |
| `title` | 子任务名称 |
| `status` | 当前状态 |
| `current` / `total` | 子任务已完成工作量与总工作量 |
| `progress` | 子任务进度，取值 0 到 100；无法计算时为空 |
| `status_message` | 当前处理阶段说明 |
| `result` | 子任务结果摘要或结果引用 |
| `error` | 子任务失败原因摘要 |
| `started_at` / `finished_at` / `updated_at` | 生命周期时间 |

第一版只支持“总任务 → 一层子任务”，不设计无限层级，避免任务树、进度聚合和取消传播过度复杂。

#### Task planning（子任务规划）

- 具体业务 Handler 实现 `build_items(task_input)`，返回可迭代的 `TaskItemSpec`。
- 每个循环元素对应一个 `TaskItemSpec`，包含标题、可序列化的 JSON 输入和可选工作总量。
- `TaskService` 在创建总任务的同一事务中完整消费迭代结果，按照返回顺序分配 `sequence` 并持久化全部子任务。
- `build_items()` 返回空结果视为任务定义错误，不创建没有子任务的总任务。
- 没有天然循环的业务仍返回单个 `TaskItemSpec`，其 `run_item()` 执行该任务的全部操作。
- `build_items()` 只解析请求参数或读取本地元数据，不访问外部服务，不执行耗时业务操作。
- 函数、闭包和 Lambda 不作为任务数据保存；总任务和子任务输入必须可序列化为 JSON。

例如日期范围 `2026-08-01` 至 `2026-08-03` 应在创建任务时生成三个稳定的子任务，Worker 只负责逐个调用 `run_item()`。

### 2. 状态模型

总任务建议状态：

```text
PENDING -> RUNNING -> SUCCEEDED
                   -> PARTIALLY_SUCCEEDED
                   -> FAILED
PENDING/RUNNING -> CANCEL_REQUESTED -> CANCELLED
```

子任务建议状态：

```text
PENDING -> RUNNING -> SUCCEEDED
                   -> FAILED
PENDING/RUNNING -> CANCELLED
PENDING -> SKIPPED
```

约束：

- 终态为 `SUCCEEDED`、`PARTIALLY_SUCCEEDED`、`FAILED` 或 `CANCELLED`，进入终态后不得继续更新进度。
- 全部子任务成功时，总任务才是 `SUCCEEDED`。
- 同时存在成功和失败子任务时，总任务是 `PARTIALLY_SUCCEEDED`。
- 全部实际执行的子任务均失败时，总任务是 `FAILED`。
- 收到取消请求后不强杀正在执行的代码；Worker 在安全检查点停止，未开始的子任务标记为 `CANCELLED` 或 `SKIPPED`。
- Worker 启动时把遗留的 `RUNNING` 或 `CANCEL_REQUESTED` 任务标记为 `FAILED`，错误摘要明确说明任务异常中断；第一版不自动续跑。
- F002.1 将为“业务工作已由历史成功记录满足”的场景扩展 `RUNNING -> SKIPPED`、总任务聚合和 Handler 结果汇总；这些扩展不属于已完成的 F002 实现。

### 3. 调度规则

- 只运行一个 Worker，任意时刻只执行一个总任务。
- `COMPUTE` 总任务的待处理子任务按稳定顺序提交到同进程线程池，最大并行度由 `ALPHAPREDATOR_COMPUTE_TASK_PARALLELISM` 配置，默认值为 1，最小值为 1。
- `EXCLUSIVE_UPDATE` 总任务的子任务继续按照稳定顺序逐个执行，并行度恒为 1。
- `COMPUTE` 表示普通计算任务，按照进入可执行队列的顺序等待。
- `EXCLUSIVE_UPDATE` 表示数据更新任务，排在所有尚未开始的 `COMPUTE` 任务之前。
- 多个 `EXCLUSIVE_UPDATE` 任务之间按照进入队列的时间顺序执行。
- 优先级不产生抢占：已经开始的任务继续运行到完成、失败或响应取消请求，之后才执行排队中的数据更新任务。
- 数据更新任务执行期间不会执行计算任务；单 Worker、单总任务模型负责保证该互斥边界。
- 创建待处理任务后，由 Web 进程确保 Worker 已按需启动；后端启动时如果发现遗留的 `PENDING` 任务，也按需启动 Worker。
- Worker 取得数据库中的单实例租约后才可领取任务；同时启动的多余 Worker 无法取得租约时退出，保证全局串行。
- Worker 处理完队列后继续等待；连续空闲 60 秒仍无新任务时释放租约并退出。
- 每个并行子任务使用独立 SQLite Session；需要读取 DuckDB 的 Handler 必须为各执行线程提供独立连接，禁止跨线程共享 Session 或 DuckDB 连接。
- 并行度只限制已经开始的子任务数量；收到取消请求后不再提交剩余子任务，已经开始的子任务仍在安全检查点响应取消。

### 4. 进度计算

- 子任务能够提供明确工作总量时，使用 `current / total` 计算进度。
- 子任务无法提前确定总量时，`progress` 为空，界面显示“处理中”和状态说明，不展示虚假的百分比。
- 所有子任务在总任务创建时由 `build_items()` 生成，使子任务总数和总任务分母保持稳定。
- 默认认为所有子任务权重相同，总进度为全部子任务进度的平均值。
- 尚未开始的子任务按 0% 计算；成功子任务固定为 100%。
- 如果未来回测中各子任务成本差异明显，再由对应 Feature 引入显式权重；F002 第一版不提前设计权重配置。
- 同一次运行期间，已展示的百分比不得倒退。

### 5. 执行边界

建议拆分为以下职责：

- `TaskService`：调用 Handler 的 `build_items()` 创建总任务及全部子任务、查询状态、请求取消和读取历史记录。
- `TaskRunner`：按固定的类型优先级串行领取待处理任务、驱动状态转换、处理异常和更新完成状态。
- `TaskHandler`：由具体业务模块实现；`build_items()` 声明循环元素，`run_item()` 执行一个元素，不直接操作任务表。
- `TaskContext`：向 Handler 提供进度上报、状态说明和取消检查能力。

业务入口（Web，未来也可能有其他入口）应复用 `TaskService`，不重复实现任务状态和进度逻辑。

后端代码按以下边界放置：

```text
backend/app/tasks/
├── models.py
├── migrations.py
├── schemas.py
├── routes.py
├── service.py
├── runner.py
├── process.py
├── worker.py
├── context.py
└── handlers/
```

- `tasks` 包拥有通用任务模型、状态流转、调度、进度、取消、Worker 生命周期和查询 API。
- 具体业务 Handler 放在 `tasks/handlers/`，但 F002 不加入生产业务 Handler。
- 业务领域客户端和数据转换仍属于对应领域包，不能全部堆入任务框架。

### 6. 运行方式选型

| 方案 | 优点 | 问题 | 建议 |
|------|------|------|------|
| FastAPI 进程内后台任务 | 实现最少 | Web 重启即中断；耗时计算会影响 API；不利于未来回测 | 不采用 |
| 独立本地 Worker 轮询 SQLite | 不引入 Redis；Web 与执行隔离；适合个人本地应用 | 需要管理额外进程和异常恢复 | 第一版采用 |
| Celery/RQ + Redis | 生态成熟、便于扩展 | 引入额外服务，对当前个人应用过重 | 暂不采用 |

当前只运行一个有效 Worker、一次只领取和执行一个总任务；`COMPUTE` 子任务在 Worker 进程内受控并行，`EXCLUSIVE_UPDATE` 子任务串行。Worker 由 Web 进程按需启动，不随应用启动而无条件常驻。

### 7. 数据存储

- 新增任务表和子任务表，具体模型及索引在实现设计阶段确定。
- 增加 Worker 单实例租约所需的最小持久化状态，避免多个独立进程同时执行任务。
- 数据库是任务状态的事实来源；前端不得根据本地计时猜测任务是否完成。
- `input`、`result` 只保存小体积 JSON 摘要或其他业务数据的引用，不把大规模回测明细塞入任务表。
- SESSION、账号、密码、访问令牌等敏感信息不得写入任务参数、状态说明或错误摘要。
- 新增表结构时必须提供迁移方案和迁移测试，不能只依赖 `create_all()` 升级已有数据库。

### 8. API 草案

| 方法 | 路径 | 用途 |
|------|------|------|
| `GET` | `/api/tasks` | 分页查询任务，可按状态和类型筛选 |
| `GET` | `/api/tasks/{task_id}` | 查询总任务详情和总体进度 |
| `GET` | `/api/tasks/{task_id}/items` | 分页查询子任务及各自进度 |
| `POST` | `/api/tasks/{task_id}/cancel` | 请求取消任务；重复请求保持幂等 |

具体业务任务的创建接口统一放在 `tasks/routes.py` 并使用对应业务的明确参数结构，内部调用 `TaskService`。F002 不提供让前端随意提交任意 `task_type` 和参数的通用创建接口，也不提供生产业务任务创建接口；具体入口从 F002.1 开始增加。

### 9. 页面草案

#### 任务列表与创建入口

- 左侧全局导航提供“任务”入口，并显示正在处理或等待处理的任务数量。
- `/tasks` 是所有业务任务创建入口的唯一归档页面；其他页面不直接提交后台任务。
- F002 尚未接入业务任务时，创建区域显示“暂无可创建的任务”，不添加演示任务。
- 默认按创建时间倒序展示。
- 每行展示任务名称、类型、状态、总体进度、成功/总子任务数、创建时间和耗时。
- 支持按状态、任务类型筛选。
- 点击任务进入详情。

#### 任务详情

- `/tasks/{task_id}` 展示单个任务详情。
- 顶部展示总任务状态、总体进度、创建/开始/结束时间、耗时和状态说明。
- 下方展示子任务列表：名称、状态、进度、耗时、最近状态说明和失败原因。
- 任务执行期间每 2 秒轮询；进入终态后停止轮询。
- 只有 `PENDING`、`RUNNING` 状态显示“取消任务”；点击后先二次确认。
- 状态使用文字和图标共同表达，不能只靠颜色区分。

## Risk

| 风险 | 解决 |
|------|------|
| Worker 异常退出后任务长期停留在 `RUNNING` | Worker 下次启动时把遗留运行状态改为明确失败，并覆盖自动化测试 |
| 并发创建任务时启动多个 Worker | Worker 执行前取得数据库单实例租约，未取得租约的进程立即退出 |
| 并行计算共享 SQLite Session 或 DuckDB 连接 | 每个计算子任务使用独立 Session；计算 Handler 按执行线程维护独立 DuckDB 连接并在汇总后关闭 |
| Worker 在队列清空与退出之间遗漏新任务 | 保留 60 秒空闲窗口；创建任务后始终执行一次按需启动检查 |
| 子任务频繁上报进度导致大量 SQLite 写入 | 限制进度写入频率，只在进度或状态发生有效变化时持久化 |
| 子任务数量过多导致详情接口和页面卡顿 | 子任务接口分页；任务表保存聚合计数，列表页不加载所有子任务 |
| 取消耗时任务不及时 | Handler 必须在可安全中断的处理边界调用取消检查；详情页明确显示“正在取消” |
| 错误信息泄露参数或敏感凭据 | 保存面向用户的错误摘要；详细异常仅写本地受控日志，并对敏感字段脱敏 |
| 回测结果体积远大于通用任务数据 | 结果由回测模块单独存储，任务模块只保存摘要和引用 |
