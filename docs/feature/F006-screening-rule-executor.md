## What

### 已确认需求

- F006 提供可承载多条选股规则的通用执行能力，首条规则为 `SR001 趋势反转`。
- 规则定义在 `docs/screening-rules/` 中独立编号、记录和维护，不把具体选股公式堆叠在 F006 Feature 文档中。
- 第一版采用“通用执行器 + 内置规则实现”：执行器统一处理任务、参数、计算日期、结果和错误语义，每条规则使用经过测试的确定性代码实现。
- Markdown 规则文档是业务定义、设计决策和验收依据，不由 Agent 或运行时直接解释为计算代码。
- 每次执行至少记录 `rule_id`、`rule_revision`、实际参数、`as_of_date` 和行情数据截止日期，使历史结果可以解释和复现。
- F006 不制作选股 Skill；未来 Agent 通过稳定的应用或 MCP 能力使用规则，不依赖 Skill 承载业务公式。

### 第一版非目标

- 不实现允许任意 JSON/YAML 公式的通用规则 DSL。
- 不执行用户提供的 Python、SQL 或其他脚本，不使用 `eval()` 解释规则。
- 不提供规则热加载、页面公式编辑器或用户上传规则文件。
- 不提供多条规则的任意 AND/OR 组合、综合评分或自动回测。
- 不在 Web 或 MCP 进程中直接读取 DuckDB。

### 待确认事项

- 第一版页面入口、筛选结果展示和历史结果查询范围。
- F006 的 MCP Tool 范围及真实客户端验收要求。
- 规则旧版本是否需要长期保留为可再次执行的实现。

## How

### 1. 总体边界

```text
页面 / MCP（待确认）
        │ 创建规则执行任务、查询 SQLite 结果
        ▼
F002 TaskService
        │ task_type + rule_id + rule_revision + parameters + as_of_date
        ▼
独立 Worker
        ├── Rule Registry：查找内置规则实现
        ├── Rule Executor：统一校验并组织执行
        ├── Indicator Library：提供口径一致的公共指标
        └── Rule Evaluator：执行具体规则并生成命中依据
        │
        ├── 读取 DuckDB 前复权日线
        └── 将子任务结果和汇总写入 SQLite
```

- F006 使用 F002 任务框架接入，生产 Handler 必须通过 `register_production_handlers()` 同时在 Web 和 Worker 注册。
- 全市场等包含股票循环的筛选由 `build_items()` 按稳定顺序生成每只股票的子任务，并统一通过 `run_item()` 执行。
- 筛选属于 `COMPUTE` 任务；F003 行情更新继续使用 `EXCLUSIVE_UPDATE`，并由现有单 Worker 串行模型避免 DuckDB 并发访问。
- Web 只在任务创建阶段读取 SQLite 股票目录等业务元数据；实际日线读取和计算只发生在 Worker。

### 2. 规则接口

每条内置规则至少声明：

- 稳定的 `rule_id` 和整数 `rule_revision`。
- 参数定义、默认值、类型和允许范围。
- 所需日线数量及其他明确的数据要求。
- 确定性的执行入口。
- 使用稳定条件编号的命中依据。

执行器只向规则提供 `as_of_date` 当日及以前的数据，禁止规则读取未来行情。具体 Python 接口在实现计划阶段确认，当前文档不提前固定类名或文件布局。

### 3. 统一结果语义

- **命中**：数据满足执行要求，且全部最终判定条件成立。
- **未命中**：数据满足执行要求，但最终判定条件不成立。
- **跳过**：数据不足、目标日期没有可用行情，或规则定义的其他不可计算情况。
- **失败**：规则注册、参数校验、数据完整性或计算过程发生异常。

每只股票的结果应包含规则标识、版本、参数、计算日期、行情截止日期、判定结果、稳定条件编号和关键指标值。不得把数据不足记作未命中，也不得生成伪造指标或伪造成功结果。

### 4. 规则演进

- 规则业务公式、默认参数或影响结果的指标口径变化时必须增加 `rule_revision`。
- 纯文案修正且不影响计算结果时不增加版本。
- 规则文档中的命中、未命中和数据不足样例应转化为自动化测试。
- 完成多条真实规则后，再根据重复模式单独评估是否引入受限 DSL；F006 第一版不为此预设表达式语言。

## Acceptance Criteria

- [ ] AC1: F006 提供统一的选股规则注册和执行入口，SR001 作为首条内置规则接入。
- [ ] AC2: 选股执行通过 F002 `COMPUTE` 任务运行；存在股票循环时，每只股票对应一个稳定子任务。
- [ ] AC3: DuckDB 日线只由独立 Worker 读取，Web 和 MCP 不直接访问 DuckDB。
- [ ] AC4: 每次执行记录规则编号、规则版本、实际参数、计算日期和行情截止日期。
- [ ] AC5: 命中、未命中、跳过和失败具有明确且互斥的语义；数据不足不记作未命中或失败。
- [ ] AC6: 每只股票的结果包含稳定条件编号及关键指标值，可以解释命中或未命中原因。
- [ ] AC7: 规则只能看到 `as_of_date` 当日及以前的数据，自动化测试覆盖未来数据隔离。
- [ ] AC8: 新增内置规则不需要新增任务框架、通用任务类型或重复的执行状态模型。
- [ ] AC9: 第一版不解释 Markdown、不执行任意脚本，也不提供通用规则 DSL 或页面公式编辑器。
- [ ] AC10: SR001 文档中的命中、未命中和数据不足样例均有对应自动化测试。
- [ ] AC11: 后端完整测试通过；如实现页面，同时通过前端构建。

## Risk

| 风险 | 解决 |
|---|---|
| 只有一条规则时过度抽象 | 第一版只抽象任务、规则接口、结果和错误语义，不建设 DSL |
| 通用接口无法适配未来所有规则 | 首版只承诺逐股票日线规则；出现横截面或其他数据规则时按真实需求扩展 |
| 规则修改导致历史结果无法解释 | 结果记录规则版本、参数和数据日期；影响结果的变化必须升级版本 |
| 通用执行器错误影响全部规则 | 对日期隔离、参数校验、跳过语义和结果序列化建立公共测试 |
| 文档与实现发生偏离 | 条件使用稳定编号，规则样例转化为测试，并在实现映射中记录对应代码 |
| 任意表达式引入安全和维护风险 | 第一版只允许注册的内置实现，禁止任意代码、SQL 和 `eval()` |
