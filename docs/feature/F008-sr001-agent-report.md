## What

### 目标

用户通过 Agent 查询一个成功完成的 SR001 模式选股任务时，Agent 可以一次取得数量受控、可解释的结构化报告和同内容 PDF；用户也可以在原有模式选股任务详情中直接下载同一份 PDF，无需新增报告页面、自行循环分页、重新执行规则或解释 Markdown 公式。

报告是 F006.4 已有确定性结果的精简表达，不是新的选股规则、二次打分模型或投资建议。

### 已确认范围

- 报告来源是状态为 `SUCCEEDED` 的已持久化 SR001 `mode_screening_analysis` 任务，必须记录来源任务公开 UUID、终态、扫描日期、扫描范围、实际 `rule_revision` 和固定参数；其他任务状态一律拒绝生成报告，不返回部分报告。
- 股票明细只保留 `pending_entry`（T 点待买入）和 `bought_today`（B 点刚买入）；`holding`、`take_profit` 和 `pending_exit` 不返回股票明细。
- 任务摘要继续返回全部命中数、T 点数、B 点数、其他当前状态的过滤数、跳过数和失败数，避免把部分成功任务表述为完整成功。
- T 点和 B 点使用独立股票池排名，不合并抢占同一名额。
- 每个状态分别生成历史胜率、平均单笔收益率和最大单笔收益率榜单；每项最多展示 10 只，不足 10 只时只展示实际数量，完全为空时标记“无符合项”。
- 榜单指标按降序排列，指标为空的股票不进入对应榜单，指标相同时按股票代码升序保证结果稳定。
- 同一股票在同一状态下可以进入多个榜单，并在每个命中的榜单中分别展示；不得为了减少重复而把三个榜单合并为一张表。
- 每个榜单直接返回自身排序后的完整股票明细和榜内名次，使 Agent 和 PDF 用户无需根据股票代码或多列名次重新组装榜单。
- 每只榜单股票至少返回股票代码和名称、T/B 状态、T 日、MACD 信号窗口、完成交易数、盈/亏/平数、胜率、平均/最大/最小单笔收益率及对应榜单名次。
- 不定义“回测样本偏少”阈值，不因完成交易数较少而过滤或降权；报告必须原样返回完成交易数，由 Agent 向用户说明样本规模。
- `insufficient_history = true` 的 T/B 股票不参与三项榜单，分别在 T 点和 B 点的“历史数据不足”区域最多展示 10 只；不足时展示实际数量，没有时省略股票明细并返回数量 0。
- 历史数据不足股票至少展示股票代码和名称、T/B 状态、T 日、实际历史区间、完成交易数和已有统计，并明确标记不参与榜单。
- 报告返回与来源任务实际 revision 对应的版本化规则摘要，包含固定参数、适用范围、D/T/B 定义、该 revision 的入选条件摘要、T/B 状态、历史数据不足定义、回测统计口径和不计交易费用/滑点等限制。
- 报告不返回完整 SR001 Markdown 规则原文，不由 Agent 重新计算或重新判定股票是否命中；已注册 Evaluator 的结果是唯一命中依据。
- 规则摘要使用独立 JSON 资源按 `rule_id` 和 `revision` 保存，不扩展现有文档 `index.json`，也不从 SR001 Markdown 中截取正文。
- 摘要文件按规则 revision 拆分，不维护独立摘要版本号；摘要文字可以直接修正或完善，由 Git 保留修改历史。摘要修改不得改变对应规则 revision 的业务语义；业务语义变化仍须新增规则 revision 和对应摘要文件。
- 固定参数的实际数值以来源任务持久化的参数为准，摘要 JSON 不重复保存参数值，避免与规则执行代码产生双重事实来源。
- 报告只能读取与来源任务 `rule_revision` 精确匹配的摘要；摘要文件缺失、结构无效或没有对应 revision 时拒绝生成报告。
- 每份摘要由 `rule_metadata` 和 `summary_data` 两块组成：前者用于精确识别规则及摘要格式版本，后者用于向 Agent 和用户解释规则在做什么。
- `rule_metadata` 包含 `rule_id`、`rule_revision`、`rule_name` 和 `source_document`；不保存摘要版本、`is_latest`、更新时间或发布状态。
- `summary_data` 包含 `purpose`、`applicable_scope`、`term_definitions`、`selection_logic`、`opportunity_states`、`trade_simulation_summary`、`insufficient_history_definition` 和 `interpretation_limits`。
- `trade_simulation_summary` 必须分别简述买入、止盈、退出和止损逻辑，使报告中的完成交易数、胜率和收益率有可理解的业务来源，不能只写成“执行历史回测”。
- 摘要 JSON 不保存完整公式、全部边界案例、具体任务统计、榜单配置、PDF 排版或通用投资风险声明；这些内容分别由规则文档、任务结果或报告层负责。
- 原有模式选股任务详情在结果区域提供“下载报告”按钮，不新增独立报告页面或网页预览组件。
- 页面入口只在任务类型为 SR001 `mode_screening_analysis`、任务状态为 `SUCCEEDED`，并且实际 `rule_revision` 已登记报告支持时显示；其他任务类型、未完成状态和未支持 revision 不显示入口。
- 点击“下载报告”后，浏览器通过后端 HTTP 下载接口即时生成并下载 PDF；接口只返回 `application/pdf`，不向页面返回 MCP 使用的结构化 JSON。
- 网页下载与 MCP Tool 必须复用同一报告组装和 PDF 生成能力，不允许页面端重新排名或后端复制一套报告业务逻辑。
- 下载文件名使用 `SR001-revision-<revision>-<扫描日期>-<task_uuid>.pdf`；生成失败时保留当前任务详情并显示后端返回的明确错误。

### 第一版非目标

- 不建设通用规则报告框架，只支持 SR001 模式选股任务。
- 不创建或重试选股任务，不重新读取 DuckDB，不重新计算 MACD、规则信号或历史回测。
- 不返回全部命中股票、未命中股票明细、全部历史交易或分次卖出明细。
- 不返回 `holding`、`take_profit` 或 `pending_exit` 股票明细。
- 不将逐股历史表现合并为组合收益、净值或资金曲线。
- 不产生实盘/模拟盘订单、自动买卖决策或投资建议。
- 不提供独立报告页面、网页内 PDF 预览、Word 导出、PDF 本地持久化、定时推送或 F007 早报/晚报联动；PDF 只在 MCP 报告 Tool 或网页下载请求期间即时生成。

## How

### 报告组织流程

```text
来源 SR001 模式选股任务（SUCCEEDED）
        │
        ├── 读取任务摘要、实际 revision 和固定参数
        ├── 仅保留 T 点待买入与 B 点刚买入
        ├── 历史数据足够：按状态分别生成并完整保留三项独立榜单
        ├── 历史数据不足：按状态单独精简展示
        ├── 附加与任务 revision 对应的规则摘要
        ├── MCP：输出结构化报告和内嵌 PDF
        └── 网页：直接下载 PDF
```

- 报告只读取 SQLite 中已持久化的任务与 F006.4 业务结果，不调用 REST 路由函数，不读取 DuckDB。
- 报告通过规则摘要加载层读取独立 JSON 资源；应用启动或自动化测试必须校验 JSON 结构，并确认受支持的 SR001 revision 均有对应摘要。
- 摘要文件按规则版本拆分；第一版路径为 `backend/app/screening/rule_summaries/SR001/revision-3.json`，不建立聚合索引文件。
- 胜率、平均收益和最大收益排名复用 F006.4 已确认的统计值，报告不引入加权总分或新的选股公式。
- 同一股票可以在多张榜单中重复出现；Agent 可以解释为“同时位于多项榜单前列”，不得改写为综合评分。
- 报告必须明确返回实际命中总数、符合 T/B 状态总数、各榜单入选数、历史数据不足总数和是否存在截断。

### 规则摘要结构

```json
{
  "rule_metadata": {
    "rule_id": "SR001",
    "rule_revision": 3,
    "rule_name": "趋势反转",
    "source_document": "docs/screening-rules/SR001-trend-reversal.md"
  },
  "summary_data": {
    "purpose": "一句话说明规则寻找什么机会",
    "applicable_scope": "规则适用范围；具体任务扫描范围仍以来源任务为准",
    "term_definitions": {
      "D": "扫描截止日",
      "T": "本轮信号首次成立日",
      "B": "T日后的首个可买入有效日"
    },
    "selection_logic": [
      "按业务顺序描述入选条件"
    ],
    "opportunity_states": {
      "pending_entry": "T点待买入的含义",
      "bought_today": "B点刚买入的含义"
    },
    "trade_simulation_summary": {
      "entry": "买入逻辑摘要",
      "take_profit": "止盈逻辑摘要",
      "exit": "退出逻辑摘要",
      "stop_loss": "止损逻辑摘要"
    },
    "insufficient_history_definition": "当前revision的数据不足定义",
    "interpretation_limits": [
      "规则或回测结果的解释边界"
    ]
  }
}
```

- `source_document` 用于回溯完整规则定义，不代表报告运行时解析该 Markdown。
- `applicable_scope` 描述规则适用范围；本次执行实际扫描的市场、股票和日期仍由来源任务返回。
- 通用的“不构成投资建议”和“历史表现不代表未来收益”等声明由报告层统一追加，不在每个规则 revision 中重复维护。

### PDF 生成与返回

- 结构化 JSON 和 PDF 必须由同一个报告数据对象生成，禁止分别查询或计算，避免两种格式内容不一致。
- PDF 在 MCP Tool 或网页下载接口调用期间使用 ReportLab 和内存字节流即时生成，不写入本地磁盘，不新增报告文件表，也不提供本地文件路径。
- MCP 使用 FastMCP 文件资源在同一次 Tool 响应中返回 `application/pdf` 内容；结构化 JSON 继续作为 Agent 可直接读取的结果。
- 网页使用 `GET /api/tasks/{task_uuid}/sr001-report.pdf` 下载 PDF；接口通过公开任务 UUID 执行与 MCP 相同的任务、状态、规则和 revision 校验，只返回 PDF 字节及下载文件名。
- 页面按钮位于原有模式选股任务详情的结果区域。点击后直接发起文件下载，不导航到新页面；下载失败时在当前页面显示错误提示。
- PDF 使用 A4 纵向版式，章节顺序固定为：报告基本信息、规则口径摘要、执行摘要、命中情况、声明；第一版不添加图表。
- “规则口径摘要”是第二章，位于执行摘要和所有股票结果之前；“命中情况”是最后一个业务数据章节，依次包含 T 点三张独立榜单及历史数据不足、B 点三张独立榜单及历史数据不足。
- 每张榜单在 A4 纵向宽度内保留已确认的完整股票统计，可通过单元格内分行组织盈/亏/平和收益指标，不得通过缩小字号使正文难以阅读。
- MACD 信号窗口在每只股票的单元格内按时间点逐行显示，revision 3 顺序为 `T-4`、`T-3`、`T-2`、`T-1`、`T`；每个值固定保留三位小数，与网页 `toFixed(3)` 展示口径一致，缺失值显示 `—`。
- 多页榜单必须重复表头并显示页码；章节标题不得与对应正文或表格分离到不同页面。
- PDF 优先使用 Windows 自带微软雅黑，缺失时尝试宋体；没有可用中文字体时返回明确错误，不生成乱码文件。
- PDF 生成后必须进行文本提取检查，并使用 Poppler 渲染全部页面，验证中文、分页、表头、列宽和页码；验证产物只放临时目录，不提交仓库。

### 规则版本支持

- `create_sr001_mode_screening_task` 不再硬编码 revision 1，而是在创建时使用已注册的 SR001 当前最新 revision 和该 revision 的固定参数；调用方仍不能传入或覆盖规则编号、版本和参数。
- 报告第一版只登记当前最新的 SR001 revision 3，不追补 revision 1、2 的摘要或报告支持。
- 后续新增 SR001 revision 时，MCP 创建 Tool 自动改用新的最新版本；新版本摘要和报告适配完成后加入支持范围，已经支持的旧 revision 报告继续可以读取，不因最新版本变化而失效。

## MCP

> 接入状态：已实现，客户端待验证。

新增 `get_sr001_screening_report(task_uuid)`，根据公开任务 UUID 一次返回结构化报告和内嵌 PDF 文件资源。Tool 只接受公开 UUID，不接受榜单数量、规则版本、参数或输出格式覆盖项。

Tool 仅接受 `SUCCEEDED` 的 `mode_screening_analysis` 任务，以及已经登记报告摘要的 SR001 revision；任务不存在、类型不匹配、状态不允许、规则不匹配、revision 未支持、摘要无效或 PDF 中文字体不可用时返回明确错误。

Hermes 任务完成通知识别 SR001 模式选股任务后，明确提示 Agent 可以调用 `get_sr001_screening_report` 获取完整报告；通知阶段不自动组装报告或生成 PDF。

MCP 只能复用任务/service 层并读取 SQLite，不得调用 REST 路由函数、打开 DuckDB、解释 Markdown 执行规则或重新计算业务结果。

## Acceptance Criteria

- [x] AC1: 用户可以基于一个 `SUCCEEDED` 的受支持 SR001 模式选股任务，一次获得同源的结构化 JSON 和内嵌 PDF；报告记录来源任务 UUID 和实际规则版本，其他状态拒绝生成。
- [x] AC2: 股票明细只包含 T 点待买入和 B 点刚买入，T/B 状态分开生成胜率、平均收益和最大收益榜单，每项最多 10 只，其他当前状态只进入过滤数量汇总。
- [x] AC3: T/B 各自返回胜率、平均收益和最大收益三个独立榜单；同一股票可以跨榜重复，每张榜单包含完整股票明细和榜内名次，不合并为去重合集。
- [x] AC4: 历史数据不足的 T/B 股票不参与榜单，按状态在独立区域最多展示 10 只，并返回总数、实际展示数和截断状态。
- [x] AC5: 报告不定义小样本阈值，每只榜单股票明确返回已完成交易数和现有胜负、收益统计。
- [x] AC6: 报告返回与来源任务 revision 对应的规则摘要和口径限制，不返回整篇 Markdown 规则原文，Agent 不重新判定是否命中。
- [x] AC6.1: 规则摘要从按 revision 拆分的独立 JSON 资源精确读取，不维护摘要版本且允许直接修正文案；固定参数实际值来自来源任务，摘要缺失或无效时拒绝生成报告。
- [x] AC6.2: 摘要严格区分规则元数据和摘要数据，交易模拟分别解释买入、止盈、退出和止损；不在摘要中重复保存任务结果、榜单配置或完整规则正文。
- [x] AC7: 报告不包含全部命中/未命中股票、完整历史交易或分次卖出明细，也不将逐股统计表述为组合收益或投资建议。
- [x] AC8: MCP 只读取 SQLite 中的任务和业务结果，不访问 DuckDB，不重新运行 SR001 选股或回测。
- [x] AC9: `get_sr001_screening_report` 即时组装报告并在内存生成 PDF，不持久化报告；Hermes 完成通知只提示按需调用，不自动生成 PDF。
- [x] AC10: MCP 创建 Tool 默认使用已注册的 SR001 最新 revision；第一版报告支持 revision 3、不支持 revision 1、2，后续新增支持不使已支持 revision 失效。
- [x] AC11: PDF 采用 A4 纵向，按基本信息、规则口径摘要、执行摘要、命中情况、声明排序；命中情况位于最后一个业务数据章节，多页表格重复表头并显示页码，中文字体缺失时明确失败。
- [x] AC11.1: 榜单中每只股票的 MACD 信号窗口按 `T-4` 至 `T` 逐行展示，数值固定保留三位小数且与网页一致，缺失值显示 `—`。
- [ ] AC12: 真实 Hermes 完成 Tool 发现、成功任务报告调用和 PDF 文件接收验证。
- [x] AC13: 符合报告条件的 SR001 模式选股任务详情在结果区域显示“下载报告”，不符合任务类型、终态或 revision 条件时不显示入口。
- [x] AC14: 点击“下载报告”后直接下载按约定命名的 PDF，不新增报告页面或网页预览，下载失败时停留在当前页面并显示明确错误。
- [x] AC15: HTTP 下载接口与 MCP Tool 复用同一报告组装和 PDF 生成逻辑，只在内存中生成文件，不持久化 PDF，也不向页面返回结构化 JSON。

## Implementation

- `backend/app/screening/sr001_report.py` 为 T/B 分别生成胜率、平均收益和最大收益三个完整榜单，同一股票允许跨榜重复。
- `backend/app/screening/sr001_report_pdf.py` 按已确认的 A4 纵向章节顺序生成六张独立榜单，并逐行显示三位小数 MACD 窗口。
- `backend/app/screening/rule_summaries/SR001/revision-3.json` 作为 revision 3 机器可读摘要，并已验证包含在后端 wheel 中。
- `backend/app/mcp_tools.py` 默认使用已注册的 SR001 最新 revision 创建任务，并通过 `get_sr001_screening_report` 返回结构化结果和内嵌 PDF。
- 自动化验证：后端 131 项通过，Hermes 插件 8 项通过；三页 PDF 完成文本提取、Poppler 全页渲染和目视检查，临时文件已删除。
- `backend/app/tasks/routes.py` 提供按公开任务 UUID 下载 PDF 的 HTTP 接口，复用既有报告对象与 PDF 生成器。
- `frontend/src/api.ts` 和 `frontend/src/components/ModeScreeningAnalysisResult.tsx` 负责内存下载、错误提示，以及成功的 SR001 revision 3 任务入口条件。
- 网页下载自动化验证：有效 PDF、响应类型、文件名，以及任务不存在、未完成、错误任务类型和不支持 revision 的错误语义均已覆盖；完整后端 148 项测试与前端生产构建通过。
- 独立榜单与纵向 PDF 验证：结构化 JSON 覆盖跨榜重复和榜内名次；七页压力样例通过 pypdf 文本、页面方向和章节顺序检查，并完成 Poppler 全页渲染及目视检查。

## Risk

| 风险 | 解决 |
|---|---|
| 一次返回数百只命中股票污染 Agent 上下文 | 只保留 T/B 状态，每项榜单最多 10 只；允许最多六张榜单间出现必要重复，以保持榜单可直接阅读 |
| 小样本高胜率被 Agent 解读为高置信度 | 不新增主观样本阈值，始终返回完成交易数、盈/亏/平数并要求 Agent 带样本规模解释 |
| 历史数据不足股票进入榜单导致横向比较失真 | 排除出三项榜单，在 T/B 独立区域返回数量、精简明细和明确警示 |
| 榜单被误解为新的综合推荐分 | 三项排名彼此独立并分别展示，不计算加权总分或合并排名 |
| 当前规则摘要误用于其他 revision 任务 | 摘要文件按规则 revision 拆分并精确匹配，不用当前默认版本覆盖其他版本语义 |
| JSON 与 PDF 分别组装导致内容不一致 | 两种输出使用同一个报告数据对象，PDF 不发起第二次业务查询或计算 |
| PDF 中文乱码或宽表格不可读 | 使用明确的 Windows 中文字体、A4 纵向和重复表头，并执行文本提取与逐页渲染检查 |
| A4 纵向无法容纳完整榜单统计 | 使用适度列宽和单元格内分行组织指标，保持可读字号，并通过全部页面渲染检查确认无裁切或重叠 |
| 运行时读取或解释 Markdown 使文档变成业务依赖 | 报告使用已确认的版本化摘要与已持久化 evidence，Markdown 只作业务定义和验收来源 |
| 部分成功、失败或取消任务被表述为完整结果 | 只允许 `SUCCEEDED` 任务生成报告，其他状态返回明确错误且不提供部分报告 |
| 网页入口与 MCP 生成不同报告 | HTTP 下载接口与 MCP Tool 复用同一个报告对象和 PDF 生成函数，页面不参与报告计算 |
| 浏览器下载造成 PDF 文件落在服务端 | 服务端继续只使用内存字节流，通过响应头触发浏览器下载，不保存文件 |
