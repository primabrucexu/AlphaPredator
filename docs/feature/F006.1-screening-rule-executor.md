## What

### 已确认需求

- 提供可承载多条选股规则的通用执行能力，规则在 `docs/screening-rules/` 中独立编号、记录和维护。
- 第一版采用“通用执行器 + 内置规则实现”：执行器统一处理任务、参数、计算日期、结果和错误语义，每条规则使用经过测试的确定性代码实现。
- Markdown 规则文档是业务定义、设计决策和验收依据，不由 Agent 或运行时直接解释为计算代码。
- 每次执行至少记录 `rule_id`、`rule_revision`、实际参数、`as_of_date` 和行情数据截止日期，使历史结果可以解释。
- `as_of_date` 表示市场选股基准日；规则可以按自身定义使用该日期及以前的个股最后有效行情，但必须返回实际计算截止日和信号日，禁止读取未来行情。
- 不制作选股 Skill；未来 Agent 通过稳定的应用或 MCP 能力使用规则，不依赖 Skill 承载业务公式。

### 第一版非目标

- 不实现允许任意 JSON/YAML 公式的通用规则 DSL。
- 不执行用户提供的 Python、SQL 或其他脚本，不使用 `eval()` 解释规则。
- 不提供规则热加载、页面公式编辑器或用户上传规则文件。
- 不负责历史买入、持有、卖出和账户净值模拟；这些能力属于 F006.2。
- 不提供多条规则的任意 AND/OR 组合或综合评分。
- 不在 Web 或 MCP 进程中直接读取 DuckDB。

- MCP Tool 范围及真实客户端验收要求。

## How

```text
页面 / MCP（待确认）
        │ 创建规则执行任务、查询 SQLite 结果
        ▼
F002 TaskService
        │ task_type + rule_id + rule_revision + parameters + as_of_date
        ▼
独立 Worker
        ├── Rule Registry：查找内置规则实现
        ├── Rule Executor：统一校验并组织执行
        ├── Indicator Library：提供口径一致的公共指标
        └── Rule Evaluator：执行具体规则并生成判定依据
        │
        ├── 读取 DuckDB 前复权日线
        └── 将子任务结果和汇总写入 SQLite
```

- 使用 F002 任务框架接入，生产 Handler 必须通过 `register_production_handlers()` 同时在 Web 和 Worker 注册。
- 存在股票循环时，由 `build_items()` 按稳定顺序生成每只股票的子任务，并统一通过 `run_item()` 执行。
- 选股属于 `COMPUTE` 任务；F003 行情更新继续使用 `EXCLUSIVE_UPDATE`。
- Web 只在任务创建阶段读取 SQLite 股票目录等业务元数据；实际日线读取和计算只发生在 Worker。

### 有效日 K 统一定义

F006.1 对第一版逐股票日线规则统一提供“有效日 K”序列：

- `open`、`high`、`low`、`close`、`volume` 必须存在且可用于计算。
- 成交量必须大于 0；没有日 K 或成交量为 0 的日期不进入有效日 K 序列。
- 一字涨停和一字跌停仍属于有效日 K；它们参与指标计算和序列计数，是否允许成交由 F006.2 和具体规则共同判断。
- 必要字段缺失或非法属于行情数据异常，不得当成停牌、历史数据不足或普通未命中。
- `t`、`t-1`、`B+1` 等基于有效日 K 的偏移，都在过滤后的个股序列上计数。

规则文档只声明指标所需字段、预热长度和对有效日 K 的额外要求，不重复定义上述基础口径。F006.2 直接复用同一有效日 K 序列，禁止另建一套日期过滤规则。

每条内置规则至少声明稳定的规则编号和整数版本、参数定义、所需数据量、确定性执行入口及使用稳定编号的判定依据。执行器只向规则提供 `as_of_date` 当日及以前的数据。

统一结果语义：

- **命中**：数据满足执行要求，且最终判定成立。
- **未命中**：数据满足执行要求，但最终判定不成立。
- **跳过**：缺少规则判断所必需的最少数据，或规则定义的其他不可计算情况。
- **失败**：规则注册、参数校验、数据完整性或计算过程发生异常。

规则可以明确允许使用不足预热长度的已有数据继续计算，但必须在结果中标记数据不足；必要行情字段缺失属于数据异常，不得与预热不足混淆。不得生成伪造指标或伪造成功结果。

## Implementation

- 规则协议、注册表、有效日 K 和统一执行结果位于 `backend/app/screening/`。
- `screening_rule_execute` Handler 在 Web 和 Worker 中统一注册；`build_items()` 按股票代码稳定排序生成子任务。
- `POST /api/tasks/screening-rule-execute` 只创建 `COMPUTE` 任务，结果继续通过通用任务及子任务查询接口读取。
- 生产注册表已接入 F006.3 的 SR001 revision 1；未注册规则仍会在任务规划阶段明确拒绝。
- 当前没有页面和 MCP Tool，规则旧版本长期执行策略仍待确认，因此 Feature 状态保持“部分完成”。

## Risk

| 风险 | 解决 |

| 只有一条规则时过度抽象 | 第一版只抽象任务、规则接口、结果和错误语义，不建设 DSL |
