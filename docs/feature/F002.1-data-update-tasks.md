## What

### 已确认需求

- 把现有韭研公社涨停数据同步迁移为后台任务。
- 把现有股票搜索目录刷新迁移为后台任务。
- 两类任务使用 F002 的 `EXCLUSIVE_UPDATE` 调度策略，优先于尚未开始的计算任务，但不抢占正在运行的任务。
- 两类任务的创建入口统一放在任务页面，不再由设置页等待同步请求执行完成。
- 韭研同步继续由用户选择开始日期和结束日期，并按日期拆分子任务。
- 韭研同步采用增量规则：执行某个日期前，检查历史韭研同步子任务；该日期存在成功执行记录时跳过，不再请求韭研接口，也不覆盖本地数据。
- 只有状态为 `SUCCEEDED` 的历史子任务才能证明该日期已经同步。历史状态为 `FAILED`、`CANCELLED` 或 `SKIPPED` 时，该日期仍需重新执行。
- 某日成功同步但返回 0 条记录，仍视为该日期已经成功执行；后续任务应跳过该日期。
- 本次任务中因历史成功记录而不再执行的日期标记为 `SKIPPED`；`SKIPPED` 按 100% 参与任务进度，但单独统计，不能计入本次成功执行数量。
- 子任务只有 `SUCCEEDED` 和 `SKIPPED` 时总任务为 `SUCCEEDED`；全部子任务均为 `SKIPPED` 时也为 `SUCCEEDED`，状态说明为“所选日期均已同步”。
- `FAILED` 与 `SUCCEEDED` 或 `SKIPPED` 并存时总任务为 `PARTIALLY_SUCCEEDED`；全部需要执行的子任务均失败且没有已满足的跳过日期时为 `FAILED`。
- Handler 完成全部子任务后生成业务结果汇总，由 Runner 写入 Task 结果；Handler 不直接修改任务表。
- Web 和 Worker 是两个独立进程，必须分别加载相同的生产 Handler 注册；两者调用同一个显式注册入口，不代表任务被创建或执行两次。
- 韭研任务类型固定为 `jygs_limit_up_sync`，TaskItem 日期字段固定为 `trade_date`，值使用 `YYYY-MM-DD`；两者共同构成增量同步记录的稳定识别方式。
- Handler 在检查历史记录后通过 `TaskItemSkipped` 报告跳过，Runner 允许子任务从 `RUNNING` 转为 `SKIPPED`；`started_at` 表示开始检查，不表示已经调用韭研接口。
- 成功的韭研 TaskItem 是增量同步依据，不得作为普通任务历史直接清理；未来增加历史清理功能时必须先迁移同步检查点。
- 正常完成或部分成功的任务在结果汇总失败时转为 `FAILED`；已经取消的任务汇总失败时保持 `CANCELLED`，同时记录真实汇总错误。
- 原有 `/api/jygs/sync` 和 `/api/stocks/sync-directory` 删除，不保留同步执行或兼容创建入口。
- 同类型任务已有 `PENDING`、`RUNNING` 或 `CANCEL_REQUESTED` 实例时拒绝重复创建，返回 `409` 和现有任务 ID。
- 一个韭研日期失败后继续执行后续日期，最终按照全部日期结果聚合为成功、部分成功或失败。
- 股票目录刷新保持现有 upsert 语义：新增和更新股票代码、名称、全拼及拼音首字母，不删除远端目录中已不存在的本地股票。
- 股票目录接口返回空列表时视为外部数据异常，任务失败，不把 0 只股票记录为成功刷新。
- 旧同步数据没有 TaskItem 记录；F002.1 上线后的首次任务重新同步用户所选范围，成功后才使用任务记录进行增量跳过。
- 第一版不提供强制重新同步已经成功执行日期的功能。
- 韭研 SESSION 只从本地凭据表读取，不得写入 Task 或 TaskItem 的输入、结果、状态说明或错误摘要。
- 外部数据源失败时记录真实失败原因，不生成伪造数据或伪造成功结果。

### 第一版范围

- 在任务页面提供“同步韭研涨停数据”和“刷新股票搜索目录”两个创建区域。
- 创建请求立即返回任务信息，用户通过任务详情查看执行状态和结果。
- 为两类业务增加生产 Task Handler，并提供统一的 `register_production_handlers()`；FastAPI 启动和独立 Worker 启动时分别调用该入口。
- 扩展通用任务执行接口，使 Handler 可以明确报告业务跳过，并在全部子任务结束后生成业务结果汇总。
- 复用现有 `app/jygs`、`StockService` 和 `MarketDataProvider` 业务边界，不把外部服务调用和业务数据转换复制到通用任务框架。
- 记录足以判断韭研日期是否成功同步的稳定 TaskItem 输入和状态。
- 展示两类任务的处理结果、跳过数量及真实失败摘要。

### 第一版非目标

- 不增加定时或无人值守的自动调度；“增量同步”只表示用户创建任务后自动跳过已经成功同步的日期。
- 不提供韭研成功日期的强制覆盖或单日重新执行。
- 不改变韭研登录和 SESSION 捕获方式。
- 不改变股票目录的数据范围，不保存行情时序数据。
- 不引入多 Worker、并发子任务、自动重试或失败子任务单独重跑。

## How

以下为基于当前代码和已确认需求形成的设计。

### 1. 韭研涨停同步任务

任务类型固定为 `jygs_limit_up_sync`。

- 一个用户选择的日期范围对应一个 Task。
- 每个自然日对应一个 TaskItem，TaskItem 输入保存 `trade_date`。
- 增量判断通过查询其他 `jygs_limit_up_sync` Task 下相同 `trade_date` 且状态为 `SUCCEEDED` 的历史 TaskItem 完成，不以 `limit_up_records` 是否存在记录作为判断依据。
- 已有成功记录的日期不调用韭研接口；本次任务保留对应 TaskItem。Runner 先把子任务标记为 `RUNNING`，Handler 完成历史检查后使用 `TaskItemSkipped` 信号报告跳过，Runner 允许 `RUNNING -> SKIPPED`，状态说明为“历史同步已成功，已跳过”。
- 没有历史成功记录的日期调用现有韭研客户端。单日成功后按现有规则覆盖该日期记录，并把记录数写入 TaskItem 结果。
- 单日失败后 Runner 保存真实错误并继续执行后续日期，不自动重试；全部日期结束后再聚合总任务状态。
- 单日任务的安全取消检查点位于外部请求之前和数据库提交之前；不强行终止已经发出的 HTTP 请求。
- Handler 在全部子任务进入终态后通过 `summarize(task, items)` 生成业务汇总，Runner 将返回值写入 Task 的 `result`。Handler 不直接写任务表。
- 韭研任务结果包含选择天数、实际执行天数、跳过天数、成功天数、失败天数和成功写入记录总数。

#### 跳过与总任务聚合

| 子任务最终情况 | 总任务状态 | 说明 |
|------|------|------|
| 只有 `SUCCEEDED` | `SUCCEEDED` | 所有日期均在本次成功执行 |
| `SUCCEEDED` 与 `SKIPPED` | `SUCCEEDED` | 本次执行成功，其余日期已有历史成功记录 |
| 只有 `SKIPPED` | `SUCCEEDED` | 所选日期均已同步，不调用外部接口 |
| `FAILED` 与 `SUCCEEDED` 或 `SKIPPED` | `PARTIALLY_SUCCEEDED` | 日期范围中一部分已满足，一部分执行失败 |
| 只有 `FAILED` | `FAILED` | 所有需要执行的日期均失败 |
| 存在因用户取消产生的 `CANCELLED` | `CANCELLED` | 取消规则继续沿用 F002 |

- `SKIPPED` 子任务的进度固定为 100%，但不增加 `completed_items`；`completed_items` 仍只表示本次成功执行的子任务数。
- 跳过数量通过 Task 业务结果中的 `skipped_days` 展示。任务页面涉及韭研任务时，应区分“本次成功”“历史已同步”和“失败”，不能把跳过显示为本次成功。
- Runner 在所有子任务结束后先确定最终状态，再调用 Handler 的 `summarize(task, items)`。正常完成或部分成功的任务汇总失败时转为 `FAILED`；已取消任务保持 `CANCELLED` 并记录汇总错误。

直接同步接口产生的旧数据没有对应 TaskItem 历史。因此迁移后的首次任务无法从业务数据判断这些日期是否执行过，会重新同步一次；成功后才由任务记录参与后续增量判断。

### 2. 股票搜索目录刷新任务

任务类型固定为 `stock_directory_refresh`。

- 一个刷新请求对应一个 Task，并只包含一个“刷新 A 股股票搜索目录”TaskItem。
- 不按股票拆成数千个 TaskItem，避免产生大量任务记录和 SQLite 写入。
- 继续通过 `MarketDataProvider.list_stocks()` 获取目录，通过 `StockService` 更新本地代码、名称、全拼和拼音首字母索引。
- Worker 进程拥有独立的 Provider 实例，并在任务结束时关闭；Handler 不直接调用 thsdk 或依赖 thsdk 响应对象。
- 获取远端目录前无法计算工作总量，界面显示不确定进度；取得目录后可以按已处理股票数报告进度。
- 保持现有整体提交语义，失败或取消时不留下半次目录刷新结果。任务进度状态与业务数据事务使用不同的数据库 Session，避免进度提交提前提交业务数据。
- 只新增或更新远端返回的股票，不删除远端目录中已不存在的本地股票。
- 行情源返回空目录时抛出明确错误，不提交业务事务，也不生成成功结果。
- `summarize(task, items)` 汇总行情源返回股票数和本地处理股票数。

### 3. 创建接口与页面

新增以下明确的业务任务创建接口：

| 方法 | 路径 | 用途 |
|------|------|------|
| `POST` | `/api/tasks/jygs-limit-up-sync` | 按日期范围创建韭研增量同步任务 |
| `POST` | `/api/tasks/stock-directory-refresh` | 创建股票搜索目录刷新任务 |

- 创建成功返回 `202 Accepted` 和 Task 信息，前端随后进入任务详情页。
- 设置页保留韭研登录、认证状态和重新登录；数据更新入口移动到 `/tasks`。
- 创建韭研任务时只校验凭据已经配置；Worker 执行具体日期时读取当前凭据并返回真实认证错误。
- 删除原有 `/api/jygs/sync` 和 `/api/stocks/sync-directory`，调用方统一迁移到任务创建接口。
- 创建任务前查询同类型活动任务；存在 `PENDING`、`RUNNING` 或 `CANCEL_REQUESTED` 实例时返回 `409 Conflict`，响应包含现有任务 ID，前端可进入该任务详情。

### 4. Handler 注册与进程边界

- Handler 注册表是进程内存状态，不通过 SQLite 在进程之间共享。
- FastAPI Web 进程需要注册 Handler，供 `TaskService` 调用 `build_items()` 并在创建任务时生成全部子任务。
- Worker 进程需要独立注册同一 Handler，供 `TaskRunner` 调用 `run_item()` 和 `summarize()`。
- 两个进程复用同一个 `register_production_handlers()` 函数，避免任务类型、Handler 实例和初始化方式分别维护。
- 注册操作只建立 `task_type` 到 Handler 的进程内映射，不创建 Task、不启动执行，也不会导致同一任务执行两次。
- 任务是否执行仍由 SQLite 中的任务状态和 F002 Worker 单实例租约决定。

## Risk

| 风险 | 解决 |
|------|------|
| 业务表中已有数据但没有历史 TaskItem | 迁移后首次任务重新同步这些日期，成功后再以 TaskItem 作为增量依据 |
| 把失败记录误判为已经同步 | 增量判断只接受 `SUCCEEDED`，失败、取消和跳过均不作为完成依据 |
| 成功的 0 条结果无法从业务表判断 | 使用成功 TaskItem 作为同步账本，不检查业务记录数量 |
| 跳过日期被误记为本次成功 | 使用明确的 `TaskItemSkipped` 信号，Runner 分别保存 `SKIPPED` 和 `SUCCEEDED` |
| 跳过子任务导致总任务失败或进度不足 100% | 把 `SKIPPED` 视为已经满足的 100% 工作量，并按已确认的状态表聚合 |
| 子任务结果存在但总任务没有业务汇总 | Runner 调用 Handler 的 `summarize(task, items)` 并持久化 Task 结果 |
| 清理任务历史导致增量检查点丢失 | 成功的韭研 TaskItem 不参与普通历史清理；未来清理前必须迁移同步检查点 |
| 同类型任务被连续创建 | 创建接口检查活动任务并返回 `409` 和现有任务 ID |
| 股票目录空响应被误报为成功 | 把空目录视为外部数据异常并回滚业务事务 |
| 历史成功后上游修正了当天数据 | 第一版不自动覆盖；未来如有需要单独设计强制重同步能力 |
| Web 或 Worker 缺少生产 Handler | 两个进程启动时分别调用统一的 `register_production_handlers()`；注册仅修改各自的进程内映射，不创建或执行任务 |
| Worker 中没有 Web 进程的 Provider 状态 | Worker Handler 管理独立 Provider 生命周期，不依赖 Web 进程的 Provider 实例 |
| 任务进度提交导致业务数据提前提交 | 股票目录业务事务与任务状态更新使用不同数据库 Session |
