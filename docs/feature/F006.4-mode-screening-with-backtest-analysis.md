## What

### 目标

用户在“模式选股”页面选择规则、扫描日期和扫描范围后，一次执行即可看到：

1. 扫描日有哪些股票出现该规则的信号。
2. 每只命中股票为什么在扫描日被选中。
3. 如果过去一直对该股票使用同一规则，其已完成交易的历史表现如何。
4. 该股票当前是否仍有等待买入、持仓、等待卖出或部分已实现的未结束交易。

F006.4 是用户可见的完整选股分析能力。F006.1、F006.2 和 F006.3 继续作为可复用的底层能力存在，但用户不需要先执行一次信号扫描，再为每只命中股票逐个手工创建回测任务。

### 已确认需求

- 页面入口继续使用“模式选股”，新任务固定使用已注册的 SR001 revision 3；历史 revision 1、2 任务继续可查看。
- 输入包含规则、扫描日期和扫描范围；扫描范围支持默认的“全市场扫描”和“指定股票”。
- 扫描日期默认使用本地行情库最新可用交易日；不得默认硬编码为 `2025-01-01` 或其他固定日期。
- 对候选股票读取其本地最早可用有效日 K 至扫描日期的行情，连续计算指标；判断当前信号时只使用扫描日期及以前的数据。
- 只展示在扫描日最终命中规则的股票；未通过 C1 的股票不执行历史回测，revision 3 的 C1 候选需要先回测以判断 L1。
- revision 3 的 MACD 延续候选只有对应交易仍处于待买入或持仓状态时才算扫描日命中；交易已全部结束的旧信号不进入报告。
- 对每只命中股票，自动复用相同的 `rule_id`、`rule_revision` 和实际参数执行个股历史回测。
- 历史回测从该股票本地最早可用行情开始，结束于扫描日期；实际可判断信号的起点仍受规则最少数据量和预热口径约束。
- SR001 历史回测继续使用其已确认的买入、TP1、EX1、SL1、T+1、部分卖出和无法成交规则，不在 F006.4 复制或修改交易公式。
- 每只命中股票展示 MACD 信号窗口、当前状态、历史回测汇总和完整交易明细；完整信号依据继续保存，但主表不重复展示必然通过的条件标签。
- MACD 信号窗口按时间顺序展示，页面统一保留 3 位小数；revision 1 历史任务显示三根，revision 2、3 显示局部低点确认及三个改善日所需的五根，不展示 DIF、DEA 或重复的当前 MACD 柱字段。
- 历史数据不足 100 根但不少于规则最少判断数据量时，沿用 SR001 的计算结果并显式标记“历史数据不足”，不伪造成正常完整历史。
- 该历史表现是逐股票独立回测，不模拟股票之间的资金竞争，也不生成跨股票组合净值。
- 胜率统一定义为 `盈利的已完成交易数 / 全部已完成交易数`；持平交易计入分母，但不计入盈利数。
- 平均、最大和最小单笔收益率只统计完全结束的交易，使用一笔交易全部卖出按原始仓位比例加权后的已实现收益率；未成交、未平仓和部分已实现交易不进入这些收益统计。
- 父任务只保存可控大小的汇总和命中股票摘要；命中股票的信号依据、统计及完整交易明细使用专用 SQLite 结果表持久化，并支持分页查询。
- 信号日保留为解释字段但不提供排序；胜率、平均收益和最大收益继续支持服务端全量排序后分页，点击顺序为降序、升序、恢复股票代码升序，排序值为空的股票始终排在最后。
- 分析结果主表展示当前状态，并支持多选筛选；多个状态之间按“或”关系匹配，筛选覆盖全部命中结果后再分页。
- 当前状态固定为：`pending_entry`（S 点待买入）、`bought_today`（B 点刚买入）、`holding`（持仓中）、`take_profit`（已执行 TP1、剩余仓位仍持有）、`pending_exit`（已锁定 EX1 或 SL1、等待卖出）。同一股票只归入一个状态，优先级为待卖出、已执行 TP1、B 点刚买入、持仓中；`pending_entry` 单独判断。
- 展开详情以一笔完整交易或活动持仓为一行；同一交易的多次卖出不得拆成多行，统一在“操作明细”列按时间顺序展示卖出日期、原因、原始仓位比例、价格和本次收益。
- 展开详情中的完成交易在数据库分页前按信号日倒序排列；第一页的当前未平仓交易置于完成交易之前，同一交易的操作明细继续按时间正序排列。
- 历史数据区间口径展示在结果上方，不占用股票表格列；统一表述为“各股票本地最早可用行情至扫描日期”，避免暗示全市场股票具有相同起始日期。

### 页面输出

任务汇总至少展示：

- 规则编号和任务实际使用的版本、扫描日期、扫描范围；历史任务必须显示其原始 revision，不得按当前默认版本覆盖。
- 候选股票数、完成数、命中数、跳过数和失败数。
- 命中股票列表。

每只命中股票至少展示：

- 股票代码和名称。
- 结果上方展示市场扫描日期及“各股票本地最早可用行情至扫描日期”的历史区间口径；股票行展示当前信号日期。
- 对应 revision 的 MACD 信号窗口；U1、U2、C1、L1 完整判定结果保留在后端 evidence 中，不占用结果主表列。
- 是否存在历史数据不足或行情异常。
- 历史已完成交易数、盈利数、亏损数和持平数。
- 历史胜率、平均单笔收益率、最大单笔收益率和最小单笔收益率。
- 展开股票后展示未成交、持仓、等待卖出、部分已实现等尚未结束的状态及数量。
- 每笔历史交易只占一行，展示信号日、实际买入日、买入价、最终状态和整笔已实现收益；各次卖出的日期、原因、比例、价格和收益率集中在该行“操作明细”列。

### 第一版非目标

- 不执行 F006.2 的全市场组合回测，不设置总资金、每笔仓位、最大持仓数或跨股票信号排序。
- 不把不同股票的个股收益简单相加或复合成组合收益、资金曲线或净值。
- 不比较多条规则，不提供规则排名、自动调参或收益最优化。
- 不修改 SR001 revision 1 的公式、固定参数或交易规则。
- 不连接券商，不产生实盘、模拟盘订单或投资建议。
- 不在 Web 或 MCP 进程中读取 DuckDB。

## How

```text
模式选股页面
  rule_id + revision + scan_date + scope
                    │
                    ▼
          F002 单个 COMPUTE 任务
                    │
                    ▼
       build_items() 按股票稳定排序
                    │ 每只股票一个子任务
                    ▼
       Worker 读取该股票完整本地历史
                    │
          ┌─────────┴─────────┐
          │ 扫描日是否命中？  │
          └─────────┬─────────┘
              否    │    是
              │     │
        记录未命中  ▼
              F006.2 个股历史回测
                    │
                    ▼
        当前信号 + 历史统计 + 交易明细
```

### 任务与执行边界

- 一次页面提交创建一个 `COMPUTE` 总任务，不要求用户先创建扫描任务再创建多个回测任务。
- `build_items()` 按股票代码稳定排序，为每只候选股票创建一个子任务。
- `run_item()` 在同一股票子任务内先判断 U1/U2/C1；revision 3 的 C1 候选执行一次历史回测判断 L1，最终命中时直接复用该结果，不重复回测。
- 该设计没有跨子任务资金或持仓状态，子任务之间互不依赖；失败股票不得阻止其他股票完成。
- Web 只负责校验输入、通过 SQLite 股票目录确定候选范围、创建任务和读取结果。
- Worker 独占读取 DuckDB，并复用 F006.1 的 Rule Evaluator、有效日 K 和 F006.2 的个股回测状态机。
- 任务和结果必须记录规则编号、整数版本、固定参数、扫描日期、实际行情范围和模型假设，保证结果可解释。

### 历史区间与未来数据隔离

- 每只股票实际读取区间为本地最早可用行情至扫描日期，股票之间允许起始日期不同。
- 不以任务创建日期、系统当前日期或固定的 `2025-01-01` 作为统一计算起点。
- 扫描日判定只能看到扫描日期及以前的数据。
- 历史回测按日期推进，每个历史信号和交易判断只能看到当时已经可用的数据。
- 扫描日期之后的行情不得用于补全未成交或未平仓交易；这些交易按扫描日截面保留真实状态。

### 结果组织

- 父任务结果保存可控大小的执行汇总和命中股票摘要。
- 每只命中股票的信号依据和统计、每笔交易及分次卖出明细使用专用 SQLite 结果表保存，并通过任务 ID 和股票代码关联。
- 结果查询必须支持页面在不加载所有未命中明细的情况下查看命中列表，并按需展开单只股票的历史交易。
- 命中股票和交易明细查询必须分页，不得依赖把全市场完整明细全部写入父任务 `result_json`。
- 新增结果表必须提供存量数据库迁移方案和迁移测试；保留周期及清理方式另行确认。

## MCP

> 接入状态：已实现。

第一版提供以下 3 个 Tool：

| Tool | 主要输入 | 行为与返回 |
|---|---|---|
| `create_sr001_mode_screening_task` | `as_of_date`, 可选 `symbols` | 创建固定使用 SR001 revision 1 的模式选股分析任务；`symbols` 为空表示规则适用的全市场；立即返回公开任务 UUID 和初始状态 |
| `get_mode_screening_results` | `task_uuid`, `page`, `page_size`, 可选 `sort_by`, `sort_order` | 分页读取命中股票、信号依据、MACD 指标、历史回测统计和未结束状态；支持按胜率、平均收益和最大收益排序 |
| `get_mode_screening_trades` | `task_uuid`, `symbol`, `page`, `page_size` | 按公开任务 UUID 和规范化股票代码分页读取完成交易及分次卖出明细 |

- 创建 Tool 不接受 `rule_id`、`rule_revision` 或 `parameters`，固定参数只能由 SR001 revision 1 定义。
- 结果 Tool 使用公开任务 UUID 和股票代码，不暴露任务、命中结果或交易记录的 SQLite 内部数字 ID。
- `sort_by` 只允许 `win_rate`、`average_return`、`maximum_return`；提供排序字段时必须同时提供 `asc` 或 `desc`，空值固定置后。
- 任务不存在、任务类型不匹配、股票未命中、分页或排序参数非法时，返回明确 Tool 错误。
- 创建后继续复用通用 `get_task` 查询状态和任务级摘要；Hermes 通知插件识别新的创建 Tool，在任务终结后向原 Session 注入一次摘要，再由 Agent 按需调用结果 Tool。
- MCP 仅复用任务/service 层并读取 SQLite，不调用 REST 路由函数，不直接访问 DuckDB。

第一版不提供通用规则执行、独立原始信号扫描、独立个股回测、全市场组合回测、规则比较或自动调参 Tool。

## Implementation

- `mode_screening_analysis` Handler 复用 F006.1 的规则执行和 F006.2 的个股回测状态机；`build_items()` 每只候选股票生成一个稳定子任务，revision 3 对 C1 候选执行一次回测判断 L1，并在最终命中时复用结果。
- `mode_screening_stock_results`、`mode_screening_trade_results` 和 `mode_screening_sale_results` 三张 SQLite 表分别保存命中股票、完成交易和分次卖出；加法迁移为股票结果增加 `current_state` 并根据原回测 JSON 回填存量结果，不改写历史交易语义。
- 父任务 `result_json` 只保存规则、扫描汇总和命中股票统计摘要，不保存完整交易明细。
- `POST /api/tasks/mode-screening-analysis` 创建任务；命中股票和交易明细分别通过任务下的分页接口读取。
- 页面命中股票分页接口支持多值 `current_state` 参数，多个值按“或”筛选并在分页前执行；只保留胜率、平均收益和最大收益的升降序参数，信号日不再支持排序。交易明细分页接口继续固定按信号日倒序查询完成交易。
- `/screening` 页面创建 SR001 revision 3 模式选股分析任务，不再要求用户先执行信号扫描、再逐只创建个股回测；旧 revision 1、2 任务仍可从历史记录进入详情。
- 真实指定股票任务 #15 已验证：`000021` 在 `2026-07-22` 命中，实际数据区间为 `2024-06-03` 至 `2026-07-22`，页面可查看 34 笔完成交易的统计、分页明细和扫描日待买入状态。
- `backend/app/tasks/operations.py` 提供 REST/MCP 共用的模式选股结果、股票定位和交易明细 SQLite 查询；MCP 适配位于 `backend/app/mcp_tools.py`，不调用 REST 路由函数。
- `create_sr001_mode_screening_task` 固定创建 SR001 revision 1 任务；`get_mode_screening_results` 和 `get_mode_screening_trades` 只返回公开 UUID、股票代码和业务结果，不返回 SQLite 内部 ID。
- Hermes 通知插件已识别新的任务创建 Tool；自动化测试和后端完整回归通过，真实 Hermes 验证待执行。

## Risk

| 风险 | 解决 |
|---|---|
| 全市场命中股票的完整交易明细使任务 JSON 过大 | 父任务只保留汇总；编码前确认专用结果结构、分页和保留策略 |
| 先扫描再创建大量依赖任务使状态和失败恢复复杂 | 一个 COMPUTE 总任务、每股一个子任务，在命中子任务内继续个股回测 |
| 不同股票上市日期不同导致历史长度不可比 | 从各自最早本地行情开始并展示实际区间和历史不足标记 |
| 个股收益被误解为组合收益 | 明确逐股票独立统计，不生成跨股票合计收益或净值 |
| 回测使用扫描日之后数据导致结果失真 | 读取上限固定为扫描日期，并建立未来数据隔离测试 |
| 全市场计算时间较长 | 未命中立即结束子任务，命中后才运行回测；页面展示总任务与子任务进度 |
